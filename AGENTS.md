## Project Custom Agent Guidance

### Project Purpose

Concierge provides personal agents, such as ChatGPT and Codex, with pre-authenticated access to the owner's accounts and capabilities that native integrations lack or expose incompletely.

- Keep this a private, personal MCP server, not a multi-user integration platform.
- Prefer broad programmatic API access over narrowly curated actions when it serves the owner's needs; keep credentials and authorization boundaries server-owned.
- Supplement native agent integrations rather than duplicate capabilities they already provide adequately.
- Keep connectors minimal and put shared authentication and reliability behavior in reusable infrastructure.

### Integration Design Principles

- Prefer thin, pre-authenticated adapters to official APIs or platform bindings. Connectors should provide access and provider-specific behavior, not recreate the provider's product or implement agent workflows.
- Preserve native API paths, query parameters, request bodies, response shapes, pagination, and attribution where practical. Let agents compose calls and process results in Code Mode; transform data only for a concrete security, compatibility, or output-size requirement.
- Keep discovery compact. Prefer a generic request method for broad REST APIs when a full SDK or generated OpenAPI catalog would add substantial schema noise. Use richer typed methods when they materially improve usability without excessive context cost; models can consult official endpoint documentation.
- The initial MCP `code` tool description must enumerate every active connector namespace, its purpose, and its primary entry point when practical. Clients should know which integrations exist before invoking tools; use discovery to select methods and retrieve detailed schemas, not to reveal the integration inventory. Keep this overview concise and aligned with the active connector set.
- Keep credentials, trusted API origins, scopes, and account identities server-owned. Support writes and deletes when intended; do not impose read-only limitations merely because callers are agents. Additional endpoint restrictions should have an explicit security, provider, or product rationale.
- Reuse shared request, validation, and authentication infrastructure and proven libraries. Keep only provider-specific contracts, authentication details, and error/replay classification in connectors; avoid parallel retry loops, speculative abstractions, and credential fallbacks.
- Make capabilities and limitations discoverable in method descriptions, not only connector-level instructions. Keep connector hints and MCP annotations aligned with actual support; distinguish API access from external-content search and interactive browsing.
- Keep integration tests credential-free and repeatable, covering native request/response behavior, credential isolation, and failure handling. Use a live read-only MCP call to verify real credentials and provider setup when available; do not treat mocks as proof of production access.

### Code Quality

- Enforce the applicable generic rules from [anti-slop](https://github.com/dmmulroy/anti-slop) with `npm run lint`; lint also gates `npm run build` and CI. The vendored plugin, licenses, exact revision, and update policy live in `tools/oxlint/anti-slop/UPSTREAM.md`; enabled rules live in `oxlint.config.ts`. Keep `oxlint` and `@oxlint/plugins` pinned to the same version.
- Preserve known types with inference or `satisfies`; do not widen values just to assert them back. Avoid chained assertions and reflective access/invocation. Each necessary non-const assertion needs a nearby `SAFETY:` comment explaining the actual invariant, not restating the cast.
- Avoid copying growing accumulators, redundant eager array passes, conditional empty-object spreads, module mocking, and vague locally owned `shape` names. Preserve callback ordering and property-omission semantics when changing existing code. Keep readable spacing between logical blocks.
- All generic anti-slop rules apply; Effect rules do not because this repo does not use Effect. Existing code or refactoring effort is not a reason to exclude a rule. Use schema-parsed types internally, concrete recursive JSON types for native API payloads, and actual library types for protocol schemas. Permit only narrow, explained inline exceptions where compliance would worsen an intentional contract, such as a parser accepting untrusted input or raw sandbox values awaiting serialization. Never evade a rule with `any`, misleading aliases, or omitted annotations.

- Explicitly declare `tools.listChanged: false` before registering tools; Concierge does not publish tool-change notifications. Do not inherit SDK capability defaults for unsupported features.
- MCP Events uses the draft webhook protocol on the same authenticated `/mcp` endpoint: `events/list`, `events/subscribe`, and `events/unsubscribe`. Cover both filter and payload descriptors in discovery regression tests.
- Event subscriptions and pending deliveries use private, prefixed SQL tables in the existing `ConciergeMcpRuntime`; preserve its binding, class identity and existing migration. Callback secrets are sealed with `jose` using a purpose-specific key derived from `COOKIE_ENCRYPTION_KEY`; never persist OAuth bearer tokens. Subscriptions default to 30 minutes, are capped at one hour and the authenticating token's expiry, and are bound to user/client/grant. Check grant authorization before delivery, handle refresh and key rotation, and remove pending work on unsubscribe/expiry/revocation. Key rotation or loss of the cookie encryption secret requires recreating subscriptions. Only metadata may be logged.
- Verify client event callbacks before sending application data. Require public HTTPS on port 443, no URL credentials/fragments, connection-time public-only fetch through `global_fetch_strictly_public`, bounded bodies/deadlines and no redirects. Use `standardwebhooks` signatures, stable event IDs across retries and fresh signing timestamps. Persist pending work before acknowledging ingress, deliver at least once with bounded retries, and do not retry 410/413 deliveries. Callback acceptance is not proof the agent completed an action. Pending message bodies are private transient delivery state, deleted after acceptance/abandonment or subscription expiry; deduplication retains IDs only for 24 hours. Bounds are 32 subscriptions, 1,024 pending deliveries and 10,000 deduplication IDs. No message archive or catch-up cursor is implemented.

Require valid `exp`, `iat`, and nonempty `sub` claims, validate `azp` when present, and return sanitized verification errors. Do not restore manual signature-only validation.

Code Mode durably limits individual values to 1,000,000 encoded bytes: keep image bytes in request-local memory behind random, execution-scoped references, never in its connector results or execution history.
